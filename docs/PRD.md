# Product Requirements Document (PRD): Link-Me v1.0

* **Status:** Draft v1.0
* **Platforms:** macOS 14+ (`MacBridge`, Swift 6 / SwiftUI `MenuBarExtra`) & Android 10+ (`AndroidBridge`, Kotlin / Jetpack Compose, minSdk 29 / targetSdk 35)
* **Architecture Principle:** Local-first, zero-cloud, peer-to-peer over local Wi-Fi (TLS 1.3 mTLS) with Bluetooth Low Energy (BLE) wake-up.

---

## 1. Problem Statement & Vision

Users working across a Mac and an Android phone lack an integrated, low-latency, privacy-preserving continuity layer comparable to Apple's Continuity suite. Existing cross-platform tools either route sensitive clipboard/notification data through third-party cloud relays, drain phone battery by holding persistent Wi-Fi sockets open, or rely on unauthenticated LAN connections.

**Link-Me** provides native macOS and Android continuity over the local network with hardware-backed mutual TLS (mTLS 1.3), BLE-gated wake-ups to preserve mobile battery life, and strict defensive boundaries around clipboards, notifications, and file writes.

---

## 2. Target Users

* **Primary:** Software engineers, designers, researchers, and power users operating a macOS workstation alongside an Android smartphone on the same local network.
* **Key Expectations:** Instant pairing, zero cloud account creation, < 50 ms LAN clipboard sync when active, < 1% daily Android background battery impact during idle periods, and strict isolation of password manager secrets.

---

## 3. Core v1.0 Features

### F1. Encrypted QR Pairing (Curve25519 + 6-Digit SAS)
* **Flow:**
  1. Initiator (macOS) displays a QR code containing its ephemeral Curve25519 (`X25519`) public key, device ID, local endpoint hint, and a random 128-bit pairing nonce.
  2. Scanner (Android) reads the QR code, generates an ephemeral `X25519` keypair, and connects over a bootstrap channel.
  3. Both sides run ECDH (`X25519`) + `HKDF-SHA256` to derive:
     * A 6-digit **Short Authentication String (SAS)** (`000000`–`999999`) displayed simultaneously on both screens.
     * A shared 256-bit `ble_beacon_key` for rotating BLE wake tokens.
     * Mutual certificate pinning commitments (`SHA-256` of peer leaf SPKI) stored in **macOS Keychain** and **Android Keystore** upon explicit user confirmation of the matching 6-digit SAS.
* **Acceptance Criteria:**
  * Pairing fails closed if SAS is rejected or times out (90 s window).
  * No long-term trust is persisted until the user taps "Confirm Match" on both devices.

### F2. Loop-Safe Universal Clipboard Sync
* **Flow:**
  1. When either device copies text/RTF/small image (v1.0 focuses on UTF-8 text up to 1 MiB), it checks platform sensitivity flags before reading/transmitting.
  2. **Sensitivity Filtering:**
     * macOS ignores pasteboard items containing `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType`, or `org.nspasteboard.AutoGeneratedType`.
     * Android ignores `ClipData` whose `ClipDescription.extras` sets `ClipDescription.EXTRA_IS_SENSITIVE == true` (API 33+) or originates from known concealed password-manager MIME/extra hints.
  3. **Loop Suppression:** Each `CLIPBOARD_SYNC` carries `originDeviceId`, `clipboardEpoch`, and `contentSha256`. A receiver applying remote clipboard content records `(contentSha256, appliedTimestamp)` in a local suppression ring buffer (2 s TTL) and tags its own pasteboard change so the local clipboard listener does not echo the item back.
* **Acceptance Criteria:**
  * Zero infinite sync ping-pong loops between Mac and Android.
  * Password manager entries never cross the network.

### F3. Chunked AirDrop-Style File Transfer
* **Flow:**
  1. Sender issues `FILE_OFFER` with `transferId` (UUID), sanitized base `filename`, `byteSize`, `sha256`, `chunkSize` (default 256 KiB), and `totalChunks`.
  2. Receiver prompts user (or auto-accepts from pinned trusted peer if configured), validates free disk space and sanitized filename, and replies with `FILE_ACCEPT` (including `resumeFromChunk` for interrupted transfers).
  3. Sender streams `FILE_CHUNK` (`0x07`) frames; receiver verifies per-chunk SHA-256 and writes sequentially to a `.part` staging file in an isolated staging directory before atomic rename upon full-file SHA-256 match.
* **Acceptance Criteria:**
  * Path traversal payloads (`../`, `..\\`, NUL bytes, absolute paths) are rejected prior to UI prompt or file creation.
  * Corrupted chunks trigger rejection/retry rather than silent file corruption.

### F4. Notification Mirroring with Inline Reply
* **Flow:**
  1. Android `BridgeNotificationListenerService` captures active non-ongoing notifications (excluding sensitive/locked-screen redacted content if configured) and emits `NOTIFICATION_POST` (`0x08`) with app metadata, `notificationKey`, `canReply`, and action descriptors.
  2. macOS presents a native `UNNotification` banner with a `UNTextInputNotificationAction` when `canReply == true`.
  3. User typing an inline reply on macOS dispatches `NOTIFICATION_REPLY` (`0x09`) back to Android, which invokes the cached `PendingIntent` + `RemoteInput` bundle to deliver the reply natively through the Android app.
* **Acceptance Criteria:**
  * Dismissing or replying on macOS cleans up the notification state and updates within < 500 ms on an active Wi-Fi link.

### F5. Battery & Ring Telemetry
* **Flow:**
  1. Periodic/on-demand `PING_TELEMETRY` (`0x02`) reports battery percentage (`0–100`), charging state (`discharging`, `charging`, `full`), current bridge state (`DORMANT_BLE`, `HANDSHAKE_WAKE`, `ACTIVE_WIFI_STREAM`, `COOLDOWN_IDLE`), thermal warning flag, and optional `ringRequested` / `ringAction` (`start`, `stop`).
  2. Triggering "Ring Phone" / "Ring Mac" plays a high-priority local alert tone (bypassing silent mode only with explicit user toggle on Android) until acknowledged or stopped after 30 s.
* **Acceptance Criteria:**
  * Telemetry uses < 256 bytes per message and piggybacks on active sessions without waking Wi-Fi unnecessarily unless "Ring" or manual refresh is triggered.

---

## 4. Non-Goals (v1.0)

* Internet / WAN relay servers or cloud accounts.
* Multi-device mesh (> 1 active simultaneous peer session; multiple paired peers may be stored, one active stream at a time).
* Camera continuity / screen mirroring / audio routing.
* Universal file sync folders (only explicit point-to-point transfers).

---

## 5. Success Metrics

| Metric | Target |
| :--- | :--- |
| Idle Android battery drain (24h `DORMANT_BLE`) | < 1.5% total battery |
| BLE wake-to-mTLS Wi-Fi ready latency | < 1,500 ms (p95) |
| Active clipboard sync latency | < 100 ms (p95) |
| File transfer throughput (Wi-Fi 5/6 LAN) | >= 25 MB/s |
| Security posture | 0 unauthenticated plaintext frames; 100% test vector pass rate |
